# 2026-11-27

## 首页加载优化（P0-1 / P0-2 / P0-3）

### 诊断结论（实测）
- 不是 "Bolt 不支持并发读"：Bolt 的 View 可并发，问题是每次 DAO 操作都 `bolt.Open`+`Close`，Open 要拿独占文件锁。
- Windows 实测：单次 open+close 6~7ms；5 个并发 open 排队 6/107/208/359/460ms；首页 DB 合计 47~55ms，共享连接 3~4ms。
- 首页最大头其实是前端阻塞式 CDN：ECharts 1.02MB/5.4s、Vue dev 612KB/2.3s、clipboard 1s（未使用），全部加载完 home.js 才发第一个请求。
- 其次：`WebsiteList` 为了判断在线调 `GetClientList`，首页又调 `/api/monitor/list`，同一批 UDP 请求做两遍；每个探针 2 次 1s 超时。

### 改动
- 前端 `__js__.html`：只保留 jQuery + Bootstrap bundle + 本地 `vue.global.prod.js`（170KB）；删除 clipboard / popper / tippy / 全局 ECharts。
- `public.js` 新增 `loadECharts()`，打开站点抽屉绘图时才从 `/static/js/echarts.min.js` 加载（1MB 不进首屏）；`renderChart` 首次调用先加载再重入。
- `dao/db.go` 重写：`Init` 只 open 一次并创建缺失桶；`Get/Set/Delete` 走 `DB.View/Update`，不再 open/close；删除 `GetDBConn`；`Close` 仅在退出调用；nil 连接返回错误而不是 panic。
- `dao/website.go`、`dao/alert.go`、`dao/request_tool.go` 改用 `DB.View`，去掉共享连接 Close。
- `dao/udp.go`：`HasOnlineMonitor()` 只读在线表；`GetClientList()` 改为纯内存轻量列表；`GetClientListDetail()` 才做 UDP 拉取且只对在线节点串行执行。
- `handler.WebsiteList` 用 `HasOnlineMonitor`；`MonitorList` 支持 `?detail=1`，探针页 `monitor.js` 带 detail，首页默认轻量。
- `main.go` 加 `defer dao.DB.Close()`。

### 关键坑（必须记住）
- udp_comm v0.0.1 **Get 不能并发**：`ID64()` 每次 new 一个 IdWorker，同毫秒生成的请求 ID 会冲突，实测 4 个并发 3 个超时、响应错配。所有 `GetAtIP` 必须串行。
- `GetClientList()` 现在没有 OS/公网 IP；需要这些字段的页面必须用 `GetClientListDetail()` 或 `?detail=1`，否则 `osInfo` 为 null。
- 单连接后，同一 data.db 不能被两个 master 进程同时打开（第二个会在 5s 超时后 panic），这是正确行为。

### 实测结果
- 首页 DB 调用 47~55ms → **4.76ms**；20 goroutine×20 次 SelectList 1ms（旧实现会排队甚至 nil panic）。
- 接口（httptest + 真实 2 站点/730 报警）：`/api/website/list` 500µs、`/api/alert/list` 6.8ms、`/api/monitor/list` 0s、`/home` 5.8ms。
- 浏览器：首页不再请求 ECharts（`typeof echarts` 为 undefined），首行数据 229ms（file:// + mock）；打开抽屉后 ECharts 正常加载并渲染 canvas。

### 后续待办
- `/api/alert/list` 现在一次返回 730 条 669KB，数据量继续涨需要分页或只返回首页所需字段。
- `GetAtWebsite` 仍是 O(n×m)，可改 map。
- 探针详情页仍是串行 UDP，节点多/有失联节点时会慢，可考虑 TTL 缓存。

## 报警列表分页（下拉加载）
- `/api/alert/list` 支持 `page/size/seg/host/kw`，返回 `list/count/page/size/hasMore/unread/counts/hosts`；`size` 不传仍返回全部，兼容旧调用。
- 报警页每页 100 条：滚动到底自动加载下一页，保留「加载更多」行兜底；切换筛选、站点、搜索时服务端过滤并重置分页；搜索 300ms 防抖。
- 首页改用 `/api/alert/list?size=5`，未读数取响应里的 `unread`，不再数字表长度。
- 新增 `/api/alert/all/read`：单个 Bolt 写事务批量置已读（505 条实测约 120ms）。
- **数据模型修复**：`entity.AlertData` 原来没有 `alertType` 字段，前端类型筛选实际一直为空。已新增字段，`AddAlert` 写入；老数据用 `alertTypeOf()` 按 Msg 推断：
  - `请求超时` / `响应时间超过` → timeout
  - `状态码` → code
  - `请求失败` → err
  - `证书` → ssl
- 实测：741 条，page1 size=100 返回 95KB/5ms（原全量 669KB），size=5 为 5KB；8 页合计 741 条无重复遗漏；`ReadAll` 后 unread=0。
- 注意：`Page` 仍是「全量读入内存 → 过滤 → 排序 → 切片」，千级数据 5ms 可接受；上万条需要索引或游标分页。

## 全局性能复查（页面数据加载）
- 日志尾部 `ReadLog`：原来是逐字节 `Seek+Read` 倒读 300 行，1MB 日志固定 **150ms**；改为按 32KB 块倒读 + 行切分，降到 **0-1ms**，同时修掉文件不存在时 `f.Close()` 空指针。
- `LogListDay` 的 `sort.Slice` 比较器误写成 `i > j`，已改 `list[i] > list[j]`；`LogList/LogListDay/DeleteLog` 从 Walk 整个日志目录改成 `filepath.Glob(host_*.log)`。
- 站点抽屉不再使用同步 XHR：`AjaxGetNotAsync` 已删除，`refreshInfo`、`loadChart`、`loadLogs`、首页/站点页编辑配置全部改异步；`loadLogs` 改为先取日期列表再取日志，避免异步后 logDay 为空。
- 探针详情 `GetClientListDetail` 加缓存：正常结果缓存 5 分钟、失败结果 30 秒；单次请求 UDP 总预算 2s、单次 Get 800ms 拆分。实测 2 个正常节点 3ms、命中缓存 0ms；1 个不响应节点 801ms、再查 0ms。
- 站点列表报警数从「每站点一次 DB 读」改为 `GetAllWebsiteAlertCounts()` 一次 View 读全表；`/api/website/list` 918B/0ms。
- 图表接口 `/api/website/chart` 改为返回 `{list, stat}`：统计用全量数据算，图表按桶取最大值降采样到 1500 点；明文 542KB→120KB，gzip 后约 9.8KB；前端兼容旧数组格式。
- `business/scan.go`：Go 1.19 循环变量复用导致所有 goroutine 扫最后一个站点，已 `v, scan := v, scan`；`ScanRate<=0` 直接 continue，避免除零 panic。
- 项目本来就有 `gin-contrib/gzip` 全局压缩（`Router.Use(gzip.Gzip(...))`），不要再加第二个压缩中间件（会双重压缩）。实测 gzip 后：`/api/website/log` 4.4KB、`/api/website/chart` 9.8KB、`/api/website/info` 2.4KB。
- 页面级结论：`/home` 5.8ms、`/sites` 4.3ms、`/api/website/list` 0.5ms、`/api/alert/list?size=100` 5ms、`/monitor` 详情缓存后 0-3ms；剩余只有「站点/报警量大时前端一次渲染全部行」的扩展性问题。

## 老 bug：unexpected EOF 被当成正常
- 根因在 gathertool v0.4.7 `context.go` 的 success 分支：`io.ReadAll` 返回 `io.ErrUnexpectedEOF` 时被显式放过（`err != io.EOF && err != io.ErrUnexpectedEOF` 才报错），响应被截断也当 200，探针记为 passed。
- 修复：`monitor/business/base.go` 的 `request()` 改原生 `net/http`，`client.Do` 后用 `io.Copy(io.Discard, io.LimitReader(body, 8MB))` 读到 EOF；读错误（含 unexpected EOF、gzip 截断）直接返回。
- 保留下载口径：仍然用 TTFB（`client.Do` 返回时）作为 UriMs，30s 超时、浏览器 UA、连接复用；避免改变慢响应报警判定。
- 新增 `isTimeoutError()`：`context.DeadlineExceeded` / `net.Error.Timeout()` 统一判超时；Health/Random/Point 三处不再用字符串匹配。`unexpected EOF` 归为 `AlertTypeErr`（请求失败），会入库并触发邮件。
- 回归测试：`monitor/business/request_test.go` 覆盖正常响应、Content-Length 未写满的截断响应、请求超时、超时分类。

## 旧 bug：修改超时时间不生效
- 根因：`master/dao/website.go` 的 `Edit` 只写 DB，**没有调用 `NoticeUpdateWebsite`**（只有 `Add` 有）。探针内存里的 `WebsiteSlowResponseTime` 一直是旧值，报警继续按旧阈值判断。
- 修复：`Edit` 三张表写成功后异步通知探针；三个 `addXxx` 的错误不再被覆盖，失败直接返回。
- 顺手修：`WebsiteEdit` 原来把 `Created` 重置为当前时间，导致扫描周期漂移；现在先读旧记录保留 `Created`。
- `WebsiteDataOut` 的 `WebsiteSlowResponseTime` 补上 `json:"websiteSlowResponseTime"`，避免依赖 JSON 大小写不敏感匹配。
- 探针慢响应消息带上实际阈值：`响应时间超过设置的报警时间(3111ms)，响应时间:5000ms`，方便直接确认用的哪套配置。
- 通知函数加 `Servers == nil` 保护，避免测试/启动早期空指针。
- 验证：编辑接口把阈值 3000 改为 3111 后，`/data/website/:hostId` 返回 3111 且 `created` 不变；`monitor/business/config_test.go` 验证探针能解析该字段（含旧的大写字段名兼容）。

## 旧 bug：采集信息 panic（whois nil conn）
- 栈：`/api/tool/website/collectInfo?host=https://www.doubao.com/` → `Collect` → `Whois` → `whois.go` 的 `net.Dial` 失败但错误被忽略，`conn=nil` 继续 `Write` → panic。
- 修复 `dao/whois.go`：`net.DialTimeout(8s)` 错误直接返回空串；`SetDeadline(15s)`；`io.ReadAll(io.LimitReader(conn,1MB))`；`defer conn.Close()` 只在连接成功后注册。
- 新增 `dao/domain.go`：`NormalizeDomain`（去协议/端口/路径/尾点）与 `rootDomain`（eTLD+1，支持 com.cn / co.uk 等）。`Whois`、`NsLookUp*`、`Collect` 全部先规范化，解决 `www.doubao.com/` 这类输入导致的 `dnsquery: DNS name contains an invalid character`。
- `Collect` 对空域名直接返回，避免 `urlStr("")` panic；`WebsiteInfoRefresh` 增加 host/id 空参数校验。
- `GetCertificateInfo` 的 `http.Client` 加 15s 超时，避免不可达站点无限挂起。
- 回归测试：`dao/domain_test.go` 覆盖 URL 规范化、eTLD+1、whois 连接失败不 panic。
